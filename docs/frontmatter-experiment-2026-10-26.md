# Эксперимент: реакция агента на новое требование frontmatter

26.10.2026 владелец предложил требовать `created` и `updated` у Markdown-файлов
и посмотреть, как агент отреагирует на имеющиеся несоответствия.

## Первый запуск

Добавлено правило `markdown-dates`, применённое ко всем выбранным `**/*.md`.
Реальный `check --all --allow-plugins --format json` вернул **exit 1 и 17 нарушений**:
16 файлов без frontmatter и один `SKILL.md` без двух новых полей. Один из 18 Markdown-файлов
уже содержал обе даты и прошёл. Исходный отчёт сохранён в `work/frontmatter-before.json`.

Это была ожидаемая реакция нового правила, а не ошибка исполнения. Ошибки не подавлялись,
уровень severity не понижался, фиктивная успешная проверка не объявлялась.

## Реакция агента

1. Прочитал диагностики и отделил отсутствие метаданных от конфликтов формата.
2. Проверил историю Git. Для 16 отслеживаемых файлов с недостающими датами первая запись
   в этом репозитории датирована 26.10.2026. Ещё один файл, `docs/self-check-2026-10-26.md`,
   создан в текущей сессии в тот же день; использовано это подтверждённое происхождение.
   Текущие timestamps файлов не выдавались за доказательство даты создания.
3. Добавил только недостающие поля. Существующие `created` и `updated` сохранены.
   Значения `2026-10-26` обоснованы историей этого проекта, а не массовым подставлением
   сегодняшнего дня ради зелёного результата. Для скопированных документов `created`
   описывает появление копии в этом репозитории, а не дату происхождения внешнего источника.
4. Сохранил тела документов при внесении frontmatter; это проверено сравнением текста
   до/после. Затем отдельно обновил актуальные README, AGENTS и описание конфигурации.
   Исторические отчёты и копии материалов AF-PM не переписывались по содержанию.
5. Сохранил исходную схему `SKILL.md`: native validator запрещает произвольные top-level
   поля. Для skill даты размещены строками в `metadata.created` и `metadata.updated`.
   Native skill validator после изменения проходит.

Трассировка по каждому файлу, источник `created` и hashes до/после находятся в
`work/frontmatter-migration.json`. Исправлено **17 файлов**, один уже соответствовал.

## Итоговые правила

```yaml
- id: markdown-dates
  kind: frontmatter
  files: ['**/*.md']
  exclude: ['skills/**/SKILL.md']
  keys: [created, updated]
- id: skill-dates
  kind: frontmatter
  files: ['skills/**/SKILL.md']
  mapping_path: [metadata]
  keys: [created, updated]
```

Исключённая из первого правила категория полностью покрыта вторым: Markdown-файлы
без проверки дат не оставлены. `mapping_path` — опциональный выбор вложенного mapping
для существующего вида `frontmatter`; прежняя проверка top-level ключей не изменена.
Literal key `metadata.created` по-прежнему означает буквальное имя ключа, а не path.
Добавлены проверки этого контракта, отсутствующих/неверных вложенных mappings и равенства
отчётов локального движка и AF Runner.

Проверены **36 тестов** движка и **16 практических сценариев** в одноразовом репозитории,
включая реальные блокируемые/успешные Git-коммиты и отказ CLI `fix` придумывать даты.
Оба pre-commit checks и Ruff проходят; native skill validator также проходит.

Повторный полный запуск после исправлений: **exit 0, 0 нарушений**. Даты остаются
явными правками агента. CLI `fix` сохраняет ограничение на безопасный newline-only fix
и не получает права придумывать или автоматически обновлять даты.

## Предел текущего правила

Проверяется наличие полей в корректном YAML mapping. Значения, ISO-формат, порядок дат,
реальное время создания и актуальность `updated` линтер пока не доказывает. Поддержание
правильного `updated` при последующих смысловых изменениях записано в AGENTS как обязанность
агента. Для проверки значений потребуется отдельное явно согласованное правило.
