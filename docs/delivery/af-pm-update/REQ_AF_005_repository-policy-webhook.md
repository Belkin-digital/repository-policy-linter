# Переносимые repository policies и проверка обновлений по webhook

## Источник и статус

Прямое указание владельца Алексея Белкина в текущей Codex-сессии 26.10.2026:
локально применять линтер при работе в Claude/Codex, при переносе в Agent Factory
сохранять все правила; предусмотреть проверку платформой работы локальных агентов
по хуку обновления репозитория, чтобы заранее тестировать постепенный переход.
Первоначальный контекст: [Настройка собственного линтера](chatgpt-conversation://6adf2038-5d5c-83ed-bfbb-d9f6d6f0950f).
Эта ссылка относится к исходному обсуждению; уточнение про webhook дано в текущем
продолжении в Codex. Его отдельный conversation id не подставлялся по догадке.

Требование принято как направление продукта. Номер инкремента, сроки, набор пилотных
репозиториев и обязательность проверки пока не назначены. Создан локальный движок
Repository Policy Linter 0.1.0 с Runner CLI bridge; это не внедрение webhook в AF.
Тикет Tracker не создан; `tracker: []` — явный остаток работы, не фиктивный номер.

## Связь с концепцией

Продолжает перенос локального workfolder/контролей в платформу из
[SoW_AF_001_platform-concept.md](../../plan/SoW/SoW_AF_001_platform-concept.md).
Использует существующие границы Runner/рабочего каталога и Core authorization;
не подменяет SCM pre-receive авторизацию проверкой содержимого и не отменяет
Policy/Approval/Audit. Контрактные `scope_NNN_*.md` этим требованием не меняются.

## Требование

1. Один версионируемый `.repo-policy.yaml` с правилами, исключениями и уровнями
   диагностик применяется локально (Claude/Codex), в CI и в AF. Engine и
   специализированные инструменты фиксируются как внешние версии/артефакты с lock/digest.
   Перенос меняет способ исполнения, а не переписывает правила в другой DSL.
2. Платформа может независимо от места работы агента проверять обновление выбранного
   репозитория: подписанный push/PR event → проверка identity/RBAC/repo Resource →
   checkout точного head SHA → детерминированный check-only Runner job → отчёт и
   check/status, привязанный к тому же SHA. Для самого lint job LLM не требуется.
3. Начальный режим наблюдательный, без блокировки merge. Он позволяет сравнить локальные
   и платформенные отчёты до переноса исполнения агента на AF. Enforce включается явно
   по выбранным репозиториям/веткам после приёмки и имеет возврат в observation.
4. Итог включает file/line/column/rule/severity/message, status/exit code, repo/head/base
   SHA, digest конфигурации и версии/digest toolchain. Dirty локальная копия не считается
   доказательством проверки опубликованного коммита. При сравнении совпадают снимок,
   all/changed file selection и approved policy revision.
5. Enforcement использует утверждённый protected baseline policy/toolchain. Изменение
   правил/плагинов в проверяемом PR анализируется отдельно и не может ослабить собственный
   обязательный gate. После принятия новой policy обе среды используют её одинаково.
6. Недоверенный код, fork, regex и plugin config исполняются только в подходящей изоляции:
   ephemeral read-only checkout, без секретов/сети по умолчанию, с ограничениями ресурсов.
   Разрешение запуска плагинов не выдаёт произвольному PR привилегированный shell Runner.
7. Webhook validation, dedup/retry, обработка superseded head и публикация статуса проходят
   существующие платформенные границы identity/RBAC/Policy/Audit. Диагностики не отправляются
   сторонним сервисам без соответствующего выбранного канала публикации и полномочий.

## Критерии приёмки

- [ ] Для одного SHA, одной policy/toolchain и одинаковой выборки локальный CLI и Runner
  дают одинаковый упорядоченный набор диагностик и код результата; регрессия покрыта тестом.
- [ ] Подписанный push/PR event разрешённого репозитория запускает проверку точного SHA;
  неизвестный Resource, неверная подпись и недопустимый actor отклоняются до исполнения.
- [ ] Повторная доставка/retry не создаёт ложных повторных эффектов; старый head не может
  опубликовать зелёный required status для нового head при out-of-order/concurrent delivery.
- [ ] Изменение/удаление policy или команды плагина в PR не позволяет обойти approved gate;
  candidate-policy report явно отделён от результата действующей утверждённой policy.
- [ ] Fork check не получает секреты и не имеет привилегированного сетевого/файлового доступа;
  проверены timeout, output limits и отказ инфраструктуры.
- [ ] Ошибка конфигурации, недоступный инструмент, недостающая Git history или падение job
  отображается как ошибка исполнения, а не clean; сохранены changed/all и structural checks.
- [ ] Observation сравнивает локальный/AF результат на одинаковом снимке и объясняет drift;
  включение/отключение enforcement не меняет правила и локальную работу агента.
- [ ] Результат/артефакт публикуется только через разрешённый канал; сохранены SHA/digests,
  audit context и разграничение прав. Native SkillVersion создаётся только через реальный Core.
